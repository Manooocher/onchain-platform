# Minimum Viable Product (MVP)

> Build the smallest possible system that proves our core research hypothesis.

---

# Purpose

The MVP is **not** intended to become a production-grade trading platform.

It is designed to validate one fundamental assumption:

> Can we automatically collect, organize, analyze, and explore newly created DEX trading pairs in a way that produces valuable research insights?

If the answer is yes, the project moves to the next stage.

---

# Core Hypothesis

Researchers lose significant time because blockchain data is fragmented across multiple tools.

A unified research workflow should dramatically reduce the effort required to investigate newly launched tokens.

The MVP exists to validate this assumption.

---

# Success Criteria

The MVP is successful if a researcher can:

- discover newly created trading pairs
- inspect their early lifecycle
- explore market activity
- review basic risk indicators
- generate reusable research datasets

without manually switching between multiple platforms.

---

# Target User

The first user of the platform is **ourselves**.

Specifically:

- quantitative researcher
- blockchain researcher
- DeFi analyst

No external users are considered during the MVP stage.

---

# Scope

The MVP focuses exclusively on newly created DEX trading pairs.

Supported lifecycle:

Pair Created

↓

Market Activity

↓

Data Collection

↓

Data Storage

↓

Basic Analysis

↓

Research

Trading execution is explicitly outside the MVP.

---

# Functional Requirements

## 1. Pair Discovery

The platform continuously detects newly created liquidity pools.

Outputs:

- chain
- pair address
- token addresses
- creation timestamp

---

## 2. Market Data Collection

Collect essential information including:

- price
- liquidity
- volume
- swap activity
- holder count (when available)
- transaction count

The objective is reliability rather than completeness.

---

## 3. Metadata Collection

Retrieve metadata including:

- token symbol
- decimals
- total supply
- contract verification status
- token age

---

## 4. Data Normalization

All incoming data must be transformed into a canonical internal format.

The rest of the platform must never depend on provider-specific APIs.

---

## 5. Data Storage

Persist collected observations inside a relational database.

The database must support:

- historical queries
- feature generation
- future ML datasets

---

## 6. Feature Generation

Generate a small set of research features.

Examples:

- liquidity growth
- volume growth
- price change
- transaction velocity
- buy/sell ratio
- token age

No advanced feature engineering is required.

---

## 7. Basic Risk Analysis

Implement deterministic rules only.

Examples:

- low liquidity
- unlocked liquidity
- suspicious ownership
- abnormal transaction activity

Machine learning is intentionally excluded.

---

## 8. Research Dashboard

Provide a simple interface allowing researchers to:

- inspect new pairs
- review collected data
- visualize feature values
- compare observations

The dashboard exists for validation rather than production usage.

---

# Non-Goals

The MVP intentionally excludes:

- automated trading
- portfolio management
- wallet authentication
- notifications
- copy trading
- strategy optimization
- reinforcement learning
- large language model integration
- multi-agent orchestration
- knowledge graph
- RAG
- distributed systems
- Kubernetes
- microservices
- high-frequency execution

These are future phases.

The MVP is strictly EVM-first. Only Ethereum, Base, and BNB Chain are supported. Non-EVM chains (e.g., Solana) are outside the scope until the core pipeline is validated.

---

# Technical Constraints

The MVP is strictly EVM-first. Only Ethereum, Base, and BNB Chain are supported. Non-EVM chains (e.g., Solana) are outside the scope until the core pipeline is validated.

The MVP must prioritize:

- simplicity
- maintainability
- fast iteration
- reproducibility

Architecture should remain modular but intentionally lightweight.

---

# Success Metrics

The MVP is considered successful if it can:

- continuously discover new trading pairs
- automatically collect their market data
- persist historical observations
- compute useful research features
- allow researchers to investigate tokens from a single interface

No profitability metrics are required during the MVP phase.

The objective is research acceleration.

---

# Deliverables

At the end of the MVP we expect:

- working data collectors
- normalized datasets
- relational database
- feature generation pipeline
- basic dashboard
- modular backend architecture
- reproducible local deployment

---

# Exit Criteria

The MVP ends when researchers consistently choose this platform over manual workflows for investigating newly launched tokens.

Only after this milestone should additional capabilities such as machine learning, strategy engines, autonomous agents, reinforcement learning, and automated execution be considered.

---

# MVP Philosophy

The MVP should answer one question only:

> Can this platform become the default research environment for on-chain quantitative analysis?

Everything else is deferred until this question has been answered.
