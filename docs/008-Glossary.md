# Canonical Glossary

> This document defines the canonical language of the platform.

Every document, module, database schema, API, AI Agent, LLM prompt, and source code must use the terminology defined here.

If another document conflicts with this glossary, **this document takes precedence.**

This glossary is intentionally technology-independent.

---

# Guiding Principles

The platform follows these semantic rules:

- Facts describe reality.
- State describes the present.
- Observations preserve history.
- Market Bars summarize trading activity.
- Features transform information.
- Outcomes provide ground truth.
- Predictions estimate Outcomes.
- Insights assist humans.

No document should redefine these concepts.

---

# A. Temporal & Data Concepts

---

## Event

Something that happened outside the platform.

Events originate from external systems.

Examples:

- Blockchain Log
- WebSocket Message
- RPC Response
- API Payload

Events are raw.

Events are not trusted until normalized.

The platform never owns Events.

---

## Fact

A verified historical occurrence derived from one or more Events.

Facts represent objective history.

Facts never represent interpretation.

Concrete implementation:

- Blockchain Fact

Fact Lifecycle:

```text
Pending

↓

Confirmed

↓

Finalized

or

Orphaned
```

Facts become immutable only after Finalization.

---

## State

The calculated representation of a system at a particular moment.

State is mutable.

State can always be reconstructed by replaying Facts.

Examples:

- Current Price
- Current Liquidity
- Pool Reserve
- Holder Count

State is never considered historical truth.

---

## State Projection

The deterministic process of transforming Facts into State.

Projection Engines continuously rebuild current system state.

State Projection is computation.

State is its result.

---

## Observation Snapshot

A timestamped recording of State.

Snapshots preserve historical context.

Observation Snapshots represent what the platform knew at a specific point in time.

Snapshots should contain state only.

Snapshots must never contain window-based analytics.

Examples:

- Current Liquidity
- Current Reserve
- Holder Count
- Market Capitalization

---

## Market Bar

An aggregation of finalized Swap Facts over a fixed time window.

Market Bars are generated directly from SwapExecuted Facts.

Never from Observation Snapshots.

Typical fields:

- Open
- High
- Low
- Close
- Volume
- Trade Count
- VWAP
- TWAP
- Buy Volume
- Sell Volume

Market Bars are primary inputs for quantitative research.

---

## Feature

A deterministic analytical transformation.

Features are derived from:

- Facts
- Observation Snapshots
- Market Bars
- Metadata

Features must never contain future information.

Examples:

- Liquidity Growth
- Buy Pressure
- Holder Growth
- Wallet Concentration
- Volatility

Features are reproducible.

---

## Outcome (Label)

A ground-truth evaluation assigned after an observation window.

Examples:

- Rug Pull
- Successful Launch
- Dead Token

Outcomes represent historical truth about the future relative to an Observation.

Outcomes have:

- observation window
- label definition
- evaluation timestamp

Outcomes never contain confidence.

Confidence belongs to Predictions.

---

## Prediction

A probabilistic estimate of an Outcome.

Predictions are generated by:

- Rule Engines
- Machine Learning
- Deep Learning
- AI Agents

Predictions may include:

- confidence
- probability
- uncertainty

Predictions are never historical truth.

---

## Insight

A human-readable research conclusion.

Insights summarize Features.

Examples:

- Suspicious Liquidity Growth
- Whale Accumulation
- High Momentum

Insights never become input to downstream pipelines.

---

# B. Structural Concepts

---

## Entity

A persistent business object.

Examples:

- Token
- Trading Pair
- Liquidity Pool
- Wallet
- Smart Contract

Entities describe the business domain.

Entities are not Events.

---

## Canonical ID

A globally unique identifier.

Every entity must have exactly one Canonical ID.

Format:

```text
eip155:<chain_id>/<entity_type>:<checksummed_address>
```

Example:

```text
eip155:8453/pair:0xAb5801a7D398351b8bE11C439e05C5B3259aeC9B
```

Canonical IDs remain stable across the platform.

---

## Metadata

Contextual information that enriches an Entity.

Examples:

- Website
- Social Links
- Logo
- Description
- Verification Status

Metadata may change.

Metadata never modifies historical Facts.

---

# C. Financial Concepts

---

## Financial Precision Principle

Floating-point numbers are prohibited.

Financial values must never use:

- float
- double

Representation:

JSON:

```text
String
```

Python:

```python
Decimal
```

Database:

```text
NUMERIC
```

Never:

- serialize float
- compare float
- store float

Precision is mandatory.

---

## Token Amount

Raw on-chain quantity.

Usually represented in smallest denomination.

Example:

```text
1000000000000000000
```

Decimals should never be applied automatically.

---

## Human Amount

A user-facing representation.

Example:

```text
1.0 ETH
```

Human Amount is derived.

Raw Amount remains canonical.

---

# D. Temporal Concepts

---

## Point-in-Time Correctness

Every computation must only use information available at that historical moment.

Future information must never influence:

- Features
- Backtests
- Machine Learning
- Research

Violating this rule creates Lookahead Bias.

---

## Lookahead Bias

Using future information during historical computation.

Lookahead Bias invalidates:

- Research
- Backtests
- ML Models

It is considered a critical architectural violation.

---

## Triple Timestamp Standard

Every processed record should distinguish between three timestamps.

### event_time

Actual blockchain time.

Usually:

```text
block_timestamp
```

---

### observed_at

Time the external provider first observed the event.

Useful for measuring provider latency.

---

### ingested_at

Time our platform successfully received the data.

Useful for:

- Debugging
- Pipeline Latency
- Monitoring

---

# E. Data Contracts

---

## Canonical Schema

The official data contract between modules.

Every pipeline communicates exclusively through Canonical Schemas.

No module should depend on:

- Provider JSON
- RPC Payload
- Third-party API Structure

---

## Schema Version

Every schema contains:

```text
schema_version
```

Breaking changes require:

- new schema version
- migration
- backward compatibility

Schemas must never change in-place.

---

# F. Storage Concepts

---

## Operational Data

Business entities required for platform operation.

Examples:

- Token
- Wallet
- Pair
- Metadata

Stored primarily in PostgreSQL.

---

## Analytical Data

Historical observations used for research.

Examples:

- Observation Snapshots
- Market Bars
- Time-Series Features

Stored primarily in TimescaleDB.

---

## Append-Only Data

Historical records that should never be modified.

Examples:

- Blockchain Facts

Append-only storage preserves reproducibility.

---

# G. AI & Research Concepts

---

## Ground Truth

Verified historical reality.

Ground Truth is represented by Outcomes.

Models learn from Ground Truth.

---

## Feature Store

A structured collection of reproducible Features.

Feature Stores guarantee consistency between:

- Training
- Validation
- Inference

---

## Research Dataset

A reproducible dataset generated from:

Facts

↓

Observations

↓

Market Bars

↓

Features

↓

Outcomes

Research datasets must satisfy Point-in-Time correctness.

---

## AI Agent

An autonomous software component that performs reasoning or execution.

Agents must consume Canonical Schemas.

Agents must never depend on provider-specific payloads.

---

## LLM Context

The structured knowledge supplied to an LLM.

LLM Context should originate only from:

- Canonical Documents
- Canonical Schemas
- Canonical Glossary

Never directly from raw provider payloads.

---

# H. Semantic Rules

The following rules are absolute.

1. Facts describe reality.
2. State is calculated.
3. Snapshots preserve State.
4. Market Bars summarize trading activity.
5. Features transform information.
6. Outcomes define Ground Truth.
7. Predictions estimate Outcomes.
8. Insights help humans.
9. Future information must never influence historical computation.
10. Canonical Schemas are the only communication contracts.
11. Financial precision is mandatory.
12. Canonical IDs uniquely identify every Entity.
13. The Glossary is the semantic source of truth for the platform.
